## 需要拦截 / 增强的事件

| 需求 | 事件 | 手段 |
|------|------|------|
| 拦过大 `limit` | `tool_call` | `return { block: true, reason }` |
| 观察全链路 | `before_agent_start` / `agent_*` / `turn_*` / `context` / … | 只打日志 |
| UI 流式输出 | （外层）`session.subscribe` → `message_update` | 不拦截 |

扩展独有（subscribe 收不到）：`tool_call`、`tool_result`、`before_agent_start`、`input`、`context` 等。

## 扩展点子

- 审计：在 `tool_execution_start/end` 记耗时与参数
- 偏好注入：在 `context` 或 `before_agent_start` 追加用户规则
- 限流监控：在 `after_provider_response` 看 429

## Lab 观察（跑完后填）

- 06a 是否打印 `[guard] blocked…`：✅ `limit=9999 (max 100)`（先有一次合法 `tool_execution_start`，随后大 limit 被拦）
- 06a 用户侧是否被解释「最多 100 行」：✅ 建议分批导出
- 06b 是否看到 `before_agent_start` / `input` / `context`：✅ 均出现；另有 `before_provider_request` / `after_provider_response`

## 收获

- 扩展独有事件才能真正拦截（`tool_call`）；`session.subscribe` 只适合观察
- `extensionFactories` + `pi.registerTool` 可把工具注册与守卫挂在同一 Runtime
